Параметрические тесты применены к классам валидации, статусам карт, фильтрам поиска, пагинации и симуляторам. Каждый параметрический запуск нарушает только одно правило.

## 4. Расхождения контракта и реализации

| Декларировано | Наблюдается | Источник | Классификация |
|---|---|---|---|
| terminal start и status | контроллер реализует start-continuous и stop, status отсутствует | OpenAPI против TerminalSimulatorController | значимый дефект контракта |
| `GET /api/simulator/merchants` доступен через общую точку входа | прямой сервис отвечает 200, Gateway отвечает 404 | SimulationController против маршрута `/api/simulator/merchant/**` | ошибка маршрутизации |
| отсутствующий terminal status должен быть 404 | Gateway возвращает 500 | экспериментальный запрос | неверное отображение ошибки |
| OpenAPI перечисляет основной набор карт | контроллер дополнительно реализует PATCH, DELETE, reserve, rollback, bulk-update | OpenAPI против CardController | неполная спецификация |
| OpenAPI не описывает часть служебных API | доступны BIN lookup и notifications | контроллеры сервисов | неполная спецификация |
| формат поля error единообразен | Gateway, Logger и Merchant используют разные значения | ответы работающего стека | несовместимый формат ошибок |
| поиск может восприниматься как поиск по STAN | TransactionFilter не содержит STAN | TransactionController и TransactionFilter | ограничение реализации |

Для ожиданий тестов источником истины выбрано наблюдаемое поведение работающего стека. Каждое несовпадение при этом оставлено в отчете, а не скрыто корректировкой теста.

## 5. Обоснование достаточности

Набор разделен на Cards, Transactions, InternalContracts и SupportingEndpoints. Общие RequestSpecification и фабрики данных находятся в support слое. Все изменения состояния выполняются через HTTP API.

Для позитивных классов проверяются тело, формат генерируемых RRN и authCode, схема карты, заголовки кэша и CSV. Для негативных классов проверяются HTTP статус, поле error, сообщение и сервис источника там, где эти поля присутствуют. Для массивов проверяются размер, фильтрация и GPath привязка к уникальному STAN.

Каждая карта создается тестом с известными балансом, лимитами и статусом. STAN, RRN, UUID и PAN создаваемых карт уникальны. Тесты не зависят от порядка и не обращаются к базе напрямую.

Асинхронная запись Gateway в Logger и карточное уведомление ожидаются через Awaitility с явными atMost и pollInterval. Отдельный тест удерживает условие отсутствия записи после невалидной транзакции через during.

Осознанно не автоматизированы аварийные 5xx каждого сервиса. Их стабильная проверка требует fault injection и управления контейнерами из тестов. Это вынесено за границы синхронного HTTP набора.

## 6. Доказательства работоспособности проверок

| Тест | Временное изменение | Полученный результат |
|---|---|---|
| `shouldCreateCardMatchingPublishedContract` | ожидаемый HTTP статус изменен с 201 на 200 | красный, фактический статус 201 |
| `shouldApproveTransactionAndReturnGeneratedValuesInContractFormat` | ожидаемый responseCode изменен с 00 на 05 | красный, фактический код 00 |
| `shouldStoreSameLoggerMessageIdempotently` | в TransactionService отключено распознавание совпадающего UUID как повтора | красный, повтор вернул 409 вместо 200 |

После каждой проверки исходный код и ожидания восстановлены. Transaction Logger пересобран из восстановленного исходника.

## 7. Порядок запуска

Полный локальный запуск одной командой:

```bash
./scripts/run-api-tests.sh
```

Скрипт создает `.env` при отсутствии, собирает и поднимает Docker Compose, ожидает состояние healthy у всех сервисов и доступность health Gateway, запускает Maven и останавливает стенд. При падении выводятся последние логи контейнеров.

Запуск только тестов на уже поднятом стеке:

```bash
mvn -f services/pom.xml -P e2e-tests -pl e2e-tests -am test -DskipE2eTests=false
```

Workflow `practice-run.yml` запускает job API tests автоматически при push в ветку `practice-5-*` и также поддерживает ручной workflow_dispatch.
